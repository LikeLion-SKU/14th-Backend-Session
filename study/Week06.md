# 데이터베이스 무결성 제약조건 정리

## 1. 개요

데이터베이스 무결성 제약조건(Constraints)은 유효하지 않은 데이터가 입력되는 것을 방지하는 역할을 한다.

## 2. 주요 무결성 제약조건

### 2.1. 엔티티 무결성 (Entity Integrity)

- **정의:** 모든 테이블은 기본키(Primary Key)를 가져야 하며, 기본키로 선택된 속성은 빈 값(NULL)을 허용하지 않고 고유해야 한다.

- **이유:** 튜플을 유일하게 식별하여 데이터 접근 및 관리의 정확성을 보장하기 위함이다.

- **구현:** `PRIMARY KEY` 제약조건.


### 2.2. 참조 무결성 (Referential Integrity)

- **정의:** 외래키(Foreign Key) 값은 참조하는 릴레이션의 기본키 값과 일치하거나 NULL이어야 한다.

- **상세 동작 (Referential Actions):** 참조되는 데이터가 삭제되거나 수정될 때의 규칙을 포함한다.

    - **CASCADE:** 참조되는 행이 삭제/수정되면 참조하는 행도 함께 삭제/수정된다.

    - **SET NULL:** 참조되는 행이 삭제/수정되면 참조하는 외래키 값을 NULL로 설정한다.

    - **RESTRICT/NO ACTION:** 참조하는 행이 존재하면 삭제/수정을 거부한다.


### 2.3. 도메인 무결성 (Domain Integrity)

- **정의:** 특정 속성의 값이 정의된 도메인(데이터 타입, 범위, 기본값 등)에 속해야 한다.

- **예시:** 나이 속성에 문자가 입력되거나, 성별 속성에 정의되지 않은 값이 들어오는 것을 방지한다.

- **구현:** 데이터 타입 설정, `DEFAULT` 선언 등.


### 2.4. 키 무결성 (Key Integrity)

- **정의:** 한 릴레이션 내의 중복된 튜플이 존재해서는 안 된다는 조건이다.

- **구현:** `UNIQUE` 제약조건 (기본키가 아니더라도 중복을 허용하지 않아야 하는 속성에 적용).


### 2.5. 범위 및 의미적 무결성 (Semantic Integrity)

- **정의:** 도메인 무결성의 확장으로, 응용 프로그램의 비즈니스 규칙에 맞는 데이터만 허용한다.

- **예시:** 나이 데이터가 숫자 형식(도메인)이더라도 음수(-10)나 비상식적인 값(200)이 입력되는 것을 제한한다.

- **구현:** `CHECK` 제약조건.


### 2.6. NULL 무결성 (NULL Integrity)

- **정의:** 특정 속성값에 NULL이 올 수 없음을 강제하는 조건이다.

- **구현:** `NOT NULL` 제약조건.

# 관계형 데이터베이스 및 JPA 연관관계 설계

## 1. 관계형 데이터베이스 (RDB) 핵심

- 데이터를 행(Row)과 열(Column)로 구성된 테이블 형태로 저장한다.

- **기본키(PK):** 테이블 내에서 행을 고유하게 식별하는 키.

- **외래키(FK):** 다른 테이블의 PK를 참조하여 테이블 간의 관계를 형성하는 키.

- **ACID 특성:** 트랜잭션의 원자성(Atomicity), 일관성(Consistency), 격리성(Isolation), 지속성(Durability)을 보장한다.


## 2. JPA 연관관계 매핑

객체의 참조 방식과 RDB의 외래키 방식 간의 차이를 ORM(JPA)을 통해 해결한다.

- **연관관계의 방향**

    - **단방향:** 한쪽 엔티티만 다른 엔티티의 참조 필드를 가지는 구조.

    - **양방향:** 양쪽 엔티티가 서로를 참조하는 구조. 이때 외래키를 관리할 '주인'을 반드시 설정해야 한다.

- **연관관계의 주인 (Owner)**

    - 외래키를 갖는 테이블 측이 주인이 되며, DB 외래키의 등록, 수정, 삭제 권한을 가진다 (`@JoinColumn` 사용).

    - 주인이 아닌 쪽은 조회(읽기)만 가능하다 (`mappedBy` 속성 사용).

- **다중성 (Multiplicity)**

    - 다대일(N:1), 일대다(1:N), 일대일(1:1), 다대다(N:M)로 구분한다.

    - `@ManyToMany`(N:M)는 추가적인 관계 데이터(예: 수강일, 성적 등)를 저장할 수 없으므로, 중간 테이블(조인 테이블)을 생성하여 1:N과 N:1 관계로 분리하는 설계가 필수적이다.

    - `@OneToMany` 위주의 설계는 불필요한 데이터 조회 및 N+1 문제를 유발할 수 있으므로, 단방향 `@ManyToOne` 중심으로 설계하는 것을 권장한다.


## 3. 조회 전략 (Fetch Type)

JPA에서 연관된 데이터를 DB에서 언제 가져올지 결정하는 전략이다.

- **즉시 로딩 (EAGER):** 엔티티 조회 시 연관된 데이터까지 한 번에 JOIN하여 가져온다. 쿼리가 복잡해지고 불필요한 데이터까지 조회되어 성능 저하의 원인이 된다.

- **지연 로딩 (LAZY):** 실제 데이터가 사용되는 시점에 쿼리를 실행하여 가져온다. 불필요한 DB 조회를 방지하므로 실무에서는 기본적으로 LAZY 사용을 권장한다.


## 4. 영속성 전이와 고아 객체

부모 엔티티의 상태 변화를 연관된 자식 엔티티에 맞추어 관리할 때 사용한다.

- **Cascade (영속성 전이):** 부모 엔티티에 수행된 작업(저장, 삭제 등)을 자식에게 전파한다. (예: `CascadeType.ALL`, `PERSIST`, `REMOVE`) .

- **orphanRemoval (고아 객체 제거):** 부모와의 연관관계가 끊어진 자식 엔티티를 DB에서 자동으로 삭제한다 (`orphanRemoval = true`).


## 5. ERD (Entity Relationship Diagram) 설계

DB 구축 전, 테이블 구조와 관계를 시각적으로 설계하고 검증하는 도구이다.

- **논리적 모델 vs 물리적 모델**

    - **Domain (논리):** 데이터의 의미를 표현하는 타입 (예: STRING, EMAIL).

    - **Type (물리):** 실제 DB에 저장되는 타입 (예: VARCHAR, BIGINT).

- **관계선의 종류**

    - **식별 관계 (실선):** 부모 테이블의 기본키(PK)를 자식 테이블의 기본키(PK)로 사용하는 관계. 자식이 부모에 강하게 종속된다.

    - **비식별 관계 (점선):** 부모 테이블의 기본키를 자식 테이블의 외래키(FK)로만 사용하는 관계. 자식이 독립적으로 존재할 수 있어 유연하다.

- **활용 도구**

    - **MySQL Workbench:** Reverse Engineer 기능을 통해 기존 데이터베이스 구조에서 ERD를 자동 추출할 수 있다.

    - **ERDCloud:** 설치 없이 실시간 협업이 가능한 웹 기반 다이어그램 도구이다.
