# 6주차 - MySQL과 ERD활용(연관관계)

>## 관계형 데이터베이스(RDB)란?  
>### 데이터를 행과 열로 구성하는 데이터베이스 유형   
>> 열 -> 데이터의 속성   
>> 행 -> 실제 데이터 값   
>> 기본키를 통해 행을 고유하게 식별   
>> 외래키를 사용해 테이블 간, 연관관계 성립  

>## 관계형 데이터베이스의 이점
>>### 1. 직관적인 데이터 구조 -> 테이블 기반 구조로, 데이터 이해와 관리 쉬움
>>### 2. 데이터 무결성 보장 -> 복잡한 데이터도 쉽게 검색 및 분석 가능
>>### 3. 데이터 정규화 지원 -> 기본키, 외래키로 데이터 관계 유지
>>### 4. SQL 기반 데이터 조회 -> 데이터 중복 감소 및 데이터 일관성 유지
>>### 5. ACID 트랜잭션 지원

>## 연관 관계
>>### 객체지향 프로그래밍 → 객체가 다른 객체를 참조하여 연관 관계 형성
>>### 관계형 데이터베이스 → 테이블이 외래키를 이용해 다른 테이블과 연결
>>### 두 방식의 관계 표현 방식이 다름 → 이를 해결하기 위해 ORM 기술 사용   

>## 연관 관계 정의 규칙
>>### 1. 방향
>>>### 단방향 연관 관계 → 주로 사용
>>>### 양방향 연관 관계 → 필요할때만 사용
>>### 2. 연관 관계 주인
>>>### 양방향 연관 관계에서, 외래키를 관리하는 주체
>>### 3. 다중성
>>>### 다대일, 일대다, 일대일, 다대다

>## 연관 관계 방향
>### 관계형 데이터베이스 → 방향 개념 존재 X
>### 객체 지향 프로그래밍 → 참조 필드가 있는 객체만 접근 가능
>>### 이로 인해, 단방향/양방향 개념 등장
>>### 양방향 사용 → 조회가 양쪽에서 모두 필요할때

>## 단방향 연관 관계
>>### 참조용 필드를 한 쪽만 가지고 있는 구조
>>### → 참조 필드가 있는 객체만 다른 객체에 접근 가능
>>>### ex) Post → User
>>>### Post 엔티티에서 User를 참조
>>>### Post는 User 조회 가능
>>>### But, User는 Post 참조하지 않음
>># 중요! DB에서는 보통 다(N)쪽 테이블이 외래키를 가짐
>>>## 구현방법
>>>### 참조필드를 가진 곳에서
>>>### @ManyToOne → 다중성 지정
>>>### @JoinColumn(name = “FK이름”)
>>>### 참조 엔티티(private User user)

>## 양방향 연관 관계
>>### 참조용 필드를 양쪽 엔티티 모두 가지고 있는 구조   
>>### → 양방향으로 객체 탐색 가능   
>>### DB에서는 동일한 구조를 가짐
>>### 그러나 객체에서 양방향에 엔티티를 참조 필드로 가지고 있음
>>### → 이로 인해 양방향 객체 탐색 가능해짐
>>>## 구현방법
>>>### 참조필드를 가지고 있던 곳은 작성법 똑같음 
>>>### 주인이 아닌 곳 → 연관관계 어노테이션(mappedBy = “엔티티”)
>
>>### 연관관계의 주인
>>### 양방향 연관 관계에서 외래키를 관리하는 기준
>>### 객체에서는 2개의 참조가 존재하지만, DB에는 동일하게 1개만 존재함

>## OneToMany를 지양하는 이유
>>## 1. 불필요한 조회 가능성
>>### 컬렉션(List) 기반 구조임
>>### → 필요 없는 데이터까지 조회될 수 있음
>>### → N+1 문제 발생 가능
>>## 2. 객체 상태 관리 부담
>>### 양쪽 객체를 직접 맞춰줘야함(동기화 해줘야함) → 실수 시 데이터 불일치 발생
>>### team.getMembers().add(member); + member.setTeam(team);
>>## 3. 실제 연관관계 주인은 따로 존재
>>### 외래키 관리 = ManyToOne
>>### OneToMany는 mappedBy 전용임
># 굳이 List를 만들어 OneToMany 방식으로 관리하지 않음
># → 차리리 리포지토리 쿼리를 통해 필요할때마다 조회하는 것이 나음

># FetchType
>### 연관된 엔티티 조회 전략
>>## FetchType.EAGER → 즉시 로딩
>>### 장점 → 연관된 데이터를 추가 조회 없이 바로 사용 가능
>>### 단점 → 조인 쿼리가 복잡해지고 성능 저하 발생 가능, 조회하지 않는 데이터까지 DB에서 가져옴
>
>>## FetchType.LAZY → 지연 로딩
>>### 장점 → 필요한 시점에만 조회 → 불필요한 DB 조회 방지
>
>>## Lazy Loading이 중요한 이유
>>### EAGER로 설정시, 불필요한 데이터까지 함께 조회됨
>>### Lazy를 사용해 필요한 순간에만 조회하고, 성능 최적화가 필요한 곳만 FETCH JOIN 사용

># 다중성
>## 엔티티 간 관계에서 한 객체가 다른 객체와 몇 개의 관계를 가질 수 있는 의미
>>### 1. 다대일
>>### 2. 일대다
>>### 3. 일대일
>>### 4. 다대다

># 다대다(N:M) 구현
>### 객체 지향 프로그래밍에서는 다대다 관계 구현 가능
>### But, 관계형 데이터베이스에서는 2개의 테이블만으로는 다대다 관계 표현 불가능
>### 따라서 조인 테이블을 이용하여, 일대다, 다대일 관계로 분리하여 구현 

># Cascade
>### 부모 엔티티의 영속성 작업을 연관된 자식 엔티티에 전파하는 기능
>>### 장점
>>### 1. 연관된 엔티티를 개별적으로 관리할 필요 X
>>### 2. 코드가 간결해지고 유지보수가 쉬움
>
>>## Type
>>### 1. CascadeType.ALL
>>### 2. CascadeType.PERSIST -> 저장
>>### 3. CascadeType.REMOVE -> 삭제
>>### 4. CascadeType.MERGE -> 병합
>>### 5. CascadeType.REFRESH -> 조회
>>### 6. CascadeType.DETATCH -> 분리
>>## 주로 사용 -> ALL, PERSIST, REMOVE
>
>>## Cascade & orphanRemoval 구조
>>### team.getMembers().remove(member); → orphanRemoval 시 해당 member 삭제
>>### teamRepository.delete(team); → Cascade Remove 시, 부모 객체가 삭제 되므로, 자식 엔티티인 member 삭제됨 
>
>>## Cascade 사용 시 주의 사항
>>### Cascade는 연관된 엔티티의 생명주기를 함께 관리할 때만 사용해야함
>>### 부모 엔티티와 강하게 의존하는 관계에서 사용하는 것이 적절
>>### 잘못 사용하면 의도하지 않은 데이터 삭제나 수정이 발생할 수 있음
>>### ex) 게시글 삭제 → 댓글 삭제 O
>>### 유저 삭제 → 게시물 모두 삭제 ? X
