# 🧩 ERD 작성 시 제약조건

## 🔹 ERD와 제약조건

- ERD(Entity Relationship Diagram)는 데이터베이스 구조를 설계하기 위한 그림
- 테이블, 컬럼, 관계, 제약조건을 미리 정리하는 데 사용
- 단순히 테이블만 나누는 것이 아니라 데이터가 올바르게 저장되도록 제약조건을 함께 고려해야 함

---

## 🔹 제약조건이란?

- 데이터베이스에 잘못된 데이터가 들어가지 않도록 제한하는 규칙
- 데이터의 정확성, 일관성, 무결성을 지키기 위해 사용
- ERD 작성 단계에서 미리 정리하면 실제 DB 구현 시 오류를 줄일 수 있음

---

## 🔹 기본키 제약조건 (Primary Key)

### ✔ 기본키란?

- 테이블에서 각 행을 구분하기 위한 고유한 값
- 하나의 테이블에는 기본키가 존재하는 것이 좋음
- 기본키 값은 중복될 수 없고, 비어 있을 수도 없음

### ✔ 기본키 제약조건

- 기본키로 지정된 컬럼은 `null` 값을 가질 수 없음
- 기본키 값은 테이블 안에서 중복될 수 없음
- 각 행을 고유하게 식별할 수 있어야 함
- 하나의 테이블에는 기본키를 하나만 설정할 수 있음

### ✔ 예시

| 테이블 | 기본키 컬럼 | 의미 |
| --- | --- | --- |
| user | id | 사용자를 구분하는 고유한 값 |
| post | id | 게시글을 구분하는 고유한 값 |

### ✔ 주의할 점

- 이름, 이메일처럼 바뀔 수 있는 값보다는 `id`처럼 변하지 않는 값을 기본키로 사용하는 것이 좋음
- 기본키는 다른 테이블에서 외래키로 참조될 수 있으므로 신중하게 정해야 함

## 🔹 외래키 제약조건 (Foreign Key)

### ✔ 외래키란?

- 다른 테이블의 기본키를 참조하는 컬럼
- 테이블 간 관계를 연결하기 위해 사용
- 데이터의 참조 무결성을 지키는 역할을 함

### ✔ 예시

- `post` 테이블의 `user_id`는 `user` 테이블의 `id`를 참조
- 하나의 게시글은 반드시 특정 사용자와 연결될 수 있음

| 테이블 | 컬럼 | 의미 |
| --- | --- | --- |
| user | id | 사용자 기본키 |
| post | user_id | user 테이블을 참조하는 외래키 |

### ✔ 외래키 제약조건이 필요한 이유

- 존재하지 않는 사용자의 게시글이 저장되는 것을 막을 수 있음
- 테이블 간 관계를 명확하게 유지할 수 있음
- 데이터의 일관성과 무결성을 보장할 수 있음

### ✔ 주의할 점

- 외래키로 참조하려는 값은 부모 테이블에 먼저 존재해야 함
- 부모 데이터 삭제 시 자식 데이터 처리 방식을 신중하게 정해야 함
- `cascade`, `set null`, `restrict` 같은 옵션을 상황에 맞게 선택해야 함

# 📚 6주차 세션 정리

## 🔹 관계형 데이터베이스 (RDB)

- RDB는 데이터를 **행과 열로 구성된 테이블 형태**로 저장하는 데이터베이스
- 테이블 간 관계는 **기본키(PK)** 와 **외래키(FK)** 를 통해 형성
- 고객 테이블과 주문 테이블 예시를 통해 PK, FK 개념을 이해할 수 있음

### ✔ RDB 장점

- 데이터 구조가 직관적임
- 데이터 무결성 보장 가능
- SQL을 사용해 데이터 검색 및 관리 가능
- ACID 트랜잭션을 지원하여 안정적인 데이터 처리 가능

---

## 🔹 객체지향과 RDB의 연관관계 차이

- 객체지향에서는 객체가 다른 객체를 참조하여 관계를 맺음
- 관계형 데이터베이스에서는 **외래키**를 통해 테이블 간 관계를 연결
- 이 차이를 해결하기 위해 **ORM 기술**을 사용

### ✔ 연관관계 설계 규칙

- 방향: 단방향, 양방향
- 다중성: N:1, 1:N, 1:1, N:M
- 외래키는 일반적으로 **N 쪽 테이블**에 위치

---

## 🔹 단방향 연관관계

- 한쪽 엔티티만 상대 엔티티를 참조하는 관계
- 예를 들어 게시글(Post)이 작성자(User)를 참조하지만, User는 Post를 직접 참조하지 않는 구조
- 단순한 구조이기 때문에 관리가 비교적 쉬움

### ✔ 예시

```java
@ManyToOne(fetch = FetchType.LAZY)
@JoinColumn(name = "user_id")
private User user;
```
## 🔹 양방향 연관관계

- 양쪽 엔티티가 서로를 참조하는 관계
- 외래키를 실제로 관리하는 쪽을 **연관관계의 주인**이라고 함
- 연관관계의 주인은 `@JoinColumn`을 사용
- 반대편은 `mappedBy`를 사용하며 읽기 전용 역할을 함

### ✔ 연관관계 주인

- 외래키를 관리하는 엔티티
- 보통 외래키가 있는 **N 쪽 엔티티**가 주인이 됨
- 주인이 아닌 쪽은 `mappedBy`로 연결

---

## 🔹 OneToMany를 지양하는 이유

- 불필요한 조회가 발생할 수 있음
- 객체 상태 관리가 복잡해짐
- N+1 문제가 발생할 가능성이 있음
- 성능 및 유지보수 측면에서 부담이 커질 수 있음

### ✔ 권장 방식

- `@OneToMany`보다 `@ManyToOne` 중심으로 설계하는 것이 좋음
- 필요한 경우에만 양방향 관계를 사용

---

## 🔹 JPA Fetch 전략

### ✔ 즉시 로딩 (Eager Loading)

- 연관된 데이터를 즉시 함께 조회하는 방식
- 사용하기 편리하지만 불필요한 JOIN이 발생할 수 있음
- 쿼리가 복잡해지고 성능이 저하될 수 있음

### ✔ 지연 로딩 (Lazy Loading)

- 실제로 연관 데이터를 사용하는 시점에 조회하는 방식
- 프록시 객체를 활용하여 필요한 순간에만 DB 조회
- 불필요한 JOIN을 줄일 수 있어 성능 최적화에 유리

### ✔ JPA 권장 방식

- 특별한 이유가 없다면 **Lazy Loading 사용 권장**
- 연관관계 매핑 시 `fetch = FetchType.LAZY`를 명시하는 것이 좋음

---

## 🔹 다중성 (Multiplicity)

- 다중성은 엔티티 간 관계의 수를 의미
- 데이터베이스 설계에서 관계 구조를 명확히 표현하기 위해 사용

### ✔ 다중성 종류

- N:1 — 여러 개가 하나를 참조
- 1:N — 하나가 여러 개를 가짐
- 1:1 — 하나가 하나와 연결
- N:M — 여러 개가 여러 개와 연결

---

## 🔹 다대다 관계 설계

- 관계형 데이터베이스에서는 N:M 관계를 직접 표현하기 어려움
- 중간 테이블을 만들어 **1:N, N:1 관계**로 분리하여 구현
- JPA의 `@ManyToMany`는 관계에 대한 추가 데이터를 저장하기 어려움

### ✔ 권장 방식

- `@ManyToMany` 사용 지양
- 중간 테이블을 별도의 엔티티로 분리
- 관계 생성일, 상태, 역할 등 추가 정보를 함께 관리 가능

---

## 🔹 Cascade

- 부모 엔티티의 변경을 자식 엔티티에 함께 전파하는 기능
- 저장, 수정, 삭제 등의 작업을 연관된 엔티티에 자동 반영할 수 있음

### ✔ Cascade Type

- `PERSIST`: 저장 전파
- `MERGE`: 병합 전파
- `REMOVE`: 삭제 전파
- `REFRESH`: 새로고침 전파
- `DETACH`: 영속성 분리 전파

### ✔ 주의할 점

- 부모와 자식의 생명주기가 강하게 연결된 경우에만 사용
- 잘못 사용하면 의도하지 않은 데이터 삭제가 발생할 수 있음

---

## 🔹 orphanRemoval

- 부모 엔티티와의 연관관계가 끊어진 자식 엔티티를 자동 삭제하는 옵션
- 고아 객체가 DB에 남는 것을 방지할 수 있음

### ✔ 사용 예시

```java
@OneToMany(mappedBy = "user", orphanRemoval = true)
private List<Post> posts;
```

## 🔹 orphanRemoval 주의할 점

- `orphanRemoval`은 부모 엔티티와의 연관관계가 끊어진 자식 엔티티를 자동으로 삭제하는 옵션
- 고아 객체가 DB에 남는 것을 방지할 수 있음
- 하지만 단순히 관계만 끊어도 데이터가 삭제될 수 있으므로 주의해야 함

### ✔ 주의할 점

- 단순히 관계만 끊어도 데이터가 삭제될 수 있음
- 삭제되어도 되는 자식 데이터에만 신중하게 사용해야 함

---

## 🔹 ERD (Entity Relationship Diagram)

- ERD는 데이터베이스의 구조를 시각적으로 표현하는 설계도
- 엔티티, 속성, 관계를 한눈에 확인할 수 있음
- 테이블 구조를 설계하고 협업할 때 유용하게 사용됨

### ✔ ERD에서 확인할 수 있는 것

- 테이블 구조
- 컬럼 정보
- 기본키와 외래키
- 테이블 간 관계
- 카디널리티

---

## 🔹 ERD 설계 도구

### ✔ ERD Cloud

- 웹 기반 무료 DB 모델링 도구
- 설치 없이 사용 가능
- 실시간 협업 가능
- SQL 생성 기능 제공

### ✔ MySQL Workbench

- GUI 기반 MySQL 관리 도구
- SQL 작성 및 실행 가능
- CSV 입출력 지원
- Reverse Engineer 기능으로 기존 DB를 ERD로 변환 가능

---

## 🔹 Domain과 Type

- Domain은 데이터가 가지는 논리적인 의미
- Type은 실제 DB에 저장되는 물리적인 데이터 타입

### ✔ 예시

| Domain | Type |
| --- | --- |
| 사용자 이름 | varchar(50) |
| 생성일 | datetime |

---

## 🔹 ERD 관계 유형

- ERD에서는 관계선을 통해 테이블 간 관계를 표현
- 카디널리티를 통해 `1:1`, `1:N`, `N:1`, `N:M` 관계를 나타냄

### ✔ 식별 관계

- 실선으로 표현
- 부모 테이블의 기본키가 자식 테이블의 기본키에도 포함되는 관계
- 부모가 없으면 자식도 존재할 수 없음

### ✔ 비식별 관계

- 점선으로 표현
- 부모 테이블의 기본키가 자식 테이블의 외래키로만 사용되는 관계
- 자식 테이블이 독립적으로 존재 가능

---

## 🔹 User - Post 연관관계 구현

- `User`와 `Post`는 `1:N` 관계
- 한 명의 사용자는 여러 게시글을 작성할 수 있음
- 하나의 게시글은 한 명의 사용자에게 속함

### ✔ 관계 구조

| 구분 | 관계 |
| --- | --- |
| User : Post | 1:N |
| Post : User | N:1 |

- 외래키 `user_id`는 `Post` 테이블에 위치함

### ✔ Post 엔티티 예시

```java
@ManyToOne(fetch = FetchType.LAZY)
@JoinColumn(name = "user_id")
private User user;
```
