## erd 작성시 인지해야 할 제약조건
제약 조건에는 크게 두가지가 있다.
1. 개체 무결성 (Entity Integrity)
2. 참조 무결성 (Referential Integrity)

- 개체 무결성: 각 테이블은 행(Row)을 고유하게 식별할 수 있는 장치를 가져야 함.
-> 하나의 개체는 유일해야 함을 뜻하며 pk로 이를 구분, null을 허용 안하며 중복 불가.
- 참조 무결성: 테이블 간의 관계를 맺을 때 데이터의 일관성을 보장해야 함.
-> null은 참조 불가. 즉, 참조를 하려면 있는 놈을 참조해야함.

### 제약조건은 아니지만 주의해야할 점
- 다대다 매핑은 사용하면 안됨.
- 되도록이면 단방향 연관관계를 사용하고, 조회를 함에 있어 양방향 설정이 필요한 경우 반드시 한쪽에 연관관계 편의 매서드를 등록해야함.
- fk는 N(many)쪽에 있어야 함.

### 연관관계의 주인(fk를 가지는 쪽)
- @JoinColumn(name = "") 사용

### 주인이 아닌 쪽(연관관계의 거울)
- @OneToOne(mappedBy) or @OneToMany(mappedBy) 사용
- 읽기만 가능, 주인이 아닌 쪽을 변경해도 db 반영 x

### 즉시로딩 vs 지연로딩
- 즉시로딩: jpa를 사용하여 db접근 시 해당 테이블과 연관관계가 맺어진 테이블들을 함께 가지고 옴.
    - 장점: 한방 쿼리로 여러개의 테이블을 가지고 올 수있음
    - 단점: 내가 필요없는 정보까지 가지고 와서 비효율 + N+1문제 쉽게 발생
- 지연로딩: jpa를 사용하여 db 접근 시 해당 데이터를 제외한 연관관계에 있는 테이블들은 가짜객체(프록시)로 가지고 옴.
    - 장점: 불필요한 쿼리가 안나감(접근시 활성화), N+1문제 발생 가능성 저하

### 그냥 지연로딩 써라.
- 지연로딩 + 패치조인, 배치사이즈 로 성능 최적화 가능


### cascade
- 부모의 영속성 작업을 자식에게 전파시키는 기능
- 부모 엔티티가 변경될때 자식 엔티티도 함께 처리되기때문에 엔티티를 개별적으로 관리 할 필요가 없음.
- 코드가 간결하고 유지보수 쉬움.

주의사항
- cascade는 연관된 엔티티의 생명주기를 함께 관리할 때만 사용해야 함

- 부모 엔티티와 강하게 의존하는 관계에서 사용하는 것이 적절

- 잘못 사용하면 의도하지 않은 데이터 삭제나 수정이 발생할 수 있음


## erd
- 데이터베이스를 실제로 구현하기 전에 데이터 구조와 테이블 간 관계를 시각적으로 표현하는 설계 도구

### 도메인 vs 타입
- Domain: 데이터의 의미를 표현하는 논리적 타입
    - ex) STRING, DATETIME,NUMBER ...
- Type: 실제 데이터베이스에 저장되는 물리적 타입
    - VARCHAR, BIGINT, DATETIME ...
### erd 설계의 필요성
#### 데이터 중복을 줄이고 구조를 명확하게 설계할 수 있으며 개발자 간 협업에도 도움이 됨
- 데이터 구조를 체계적으로 설계 가능

- 테이블 간 관계 명확화

- 데이터 중복 최소화

- 개발자 간 협업 및 구조 이해 용이

- 실제 DB 구현 전 설계 검증 가능
