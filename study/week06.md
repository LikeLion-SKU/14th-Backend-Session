## 관계형 데이터베이스 (RDB)
- 데이터를 행과 열로 구성하는 데이터베이스 유형
- 데이터를 테이블 형태로 저장
- 열 (column)
  - 데이터의 속성
- 행 (row)
  - 실제 데이터 값
- 기본키
  - 행을 고유하게 식별하는 기본 키
- 외래키
  - 다른 테이블의 기본 키를 참조하는 키

### 관계형 데이터베이스의 이점
- 직관적인 데이터 구조
- 데이터 무결성 보장
- SQL 기반 데이터 조회
- 데이터 정규화 지원
  - 정규화 ?
    - 데이터 중복을 줄이고 데이터 구조를 형식에 맞춰 정리하는 설계 기법
- ACID 트랜잭션 지원

### 연관 관계
- 객체 지향과 관계형 데이터베이스의 관계 표현 방식
- 객체 지향 프로그래밍
  - 객체가 다른 객체를 **참조**해 연관 관계 형성
- 관계형 데이터베이스
  - 테이블이 **외래키**로 다른 테이블과 연결

=> 두 관계의 표현 방식이 다르기 때문에 **ORM**을 이용하여 해결

#### 연관 관계 정의 규칙
- 방향
  - 단방향과 양방향으로 구성
- 연관 관계 주인
  - 양방향 연관 관계에서 **외래키를 관리하는 주체**
- 다중성
  - 엔티티 간 관계에서 한 객체가 다른 객체와 몇 개의 관계를 가질 수 있는지 나타냄
  - 종류
    - 다대일
    - 일대다
    - 일대일
    - 다대다

#### 연관 관계 방향
- 관계형 DB
  - 방향 개념이 존재하지 않음
- 객체 지향 프로그래밍
  - 단방향, 양방향 연관 관계로 나뉨

#### 단방향 연관 관계
- 한쪽 엔티티만 다른 엔티티를 참고하는 구조
- JPA가 자동으로 컬럼명을 생성해주지만 가독성을 위해 **@JoinColumn** 사용을 권장
- @ManyToOne을 중심으로 설계
- 필요하면 Query 조회 방식이 적절 (Repository에서)

#### 양방향 연관 관계
- 양쪽 엔티티가 서로를 참조하는 구조
- DB 구조가 아니고 Entity 설계할때 정의되는 개념
- **@OneToMany(mappedBy = “”)**
    - 주인이 아니고 읽기 전용이다 알려주는 어노테이션
    - 불필요한 조회 가능성, 객체 상태 관리 부담, 실제로 연관관계 주인은 따로 존재
      - 필요 없는 데이터를 조회할 수 있음
      - @OneToMany는 지양하는 편
- 주인이 필요함

#### 연관 관계의 주인
- 주인 (Owner)
  - @JoinColumn 사용
  - 외래키가 있는 테이블이 주인이 됨
- 주인이 아닌 쪽
  - 읽기만 가능 (mappedBy 사용) 

### Fetch Type
- JPA에서 연관된 데이터를 DB에서 언제 조회할지 결정하는 전략
- 종류
  - **Eager Loading**
    - 즉시 로딩
    - 연관된 엔티티를 미리 가져오는 것
    - 조회하지 않는 연관 데이터가까지 DB에서 가져오기 때문에 자주 사용하진 않음
  - **Lazy Loading**
    - 지연 로딩
    - 연관된 엔티티를 필요할 때 가져오는 것
    - 필요한 시점에만 조회를 하기 때문에 성능 최적화면에서 사용을 권장

### 다중성
- 다대일 (N:1)
  - 여러 개의 객체가 하나의 객체를 참조하는 관계
  - @ManyToOne
- 일대다 (1:N)
  - 하나의 객체가 여러 개의 객체를 참조하는 관계
  - @OneToMany
- 일대일 (1:1)
  - 하나의 객체가 다른 하나의 객체와만 연결되는 관계
  - @OneToOne
- 다대다 (N:M)
  - 여러 개의 객체가 여러 개의 객체와 연결되는 관계 
  - @ManyToMany
  - 객체 지향 프로그래밍에서는 표현할 수 있지만 관계형 데이터베이스에서는 표현할 수 없음
    => **중간 테이블**을 생성해 N:1 과 1:N 관계로 분리해 구현

### Cascade
- 부모 엔티티의 영속성 작업을 연관된 자식 엔티티에 전파하는 기능
- 부모 엔티티가 변경되면 자식 엔티티도 같이 변경됨
- 종류
  - **ALL**
    - 모든 영속성 작업을 자식 엔티티에 전파
  - **PERSIST**
    - 부모 엔티티를 저장할 때 자식 엔티티도 저장
  - **REMOVE**
    - 부모 엔티티를 삭제할 때 자식 엔티티도 삭제
  - MERGE
  - REFRESH
  - DETACH

#### Cascade & orphanRemoval 구조
- 부모가 자식을 직접 관리하는 구조
- **orphanRemoval**
  - 부모 엔티티와의 연관 관계가 끊어진 자식 엔티티(고아 객체)를 DB에서 자동으로 삭제하는 것
  - **cascade = Cascade.ALL** 과 같이 쓰임
  - Cascade REMOVE를 하게 되면 고아 데이터가 발생할 수 있음 -> orphanRemoval 사용해 고아 데이터 발생 방지
- ex)
  - `@OneToMany(
    mappedby = "team",
    cascade = CascadeType.ALL,
    orphanRemoval = true
)
private List<Member> members = new ArrayList<>();`

## ERD
- 데이터베이스를 실제로 구현하기 전에 데이터 구조와 테이블 간 관계를 시각적으로 표현하는 설계 도구
- 엔티티, 속성, 관게로 구성되어 있음

### Domain 과 Type
- Domain
  - 데이터의 의미를 표현하는 논리적 데이터 타입
  - STRING, NUMBER, EMAIL 등
- Type
  - 실제 데이터베이스에 저장되는 물리적인 데이터 타입
  - VARCHAR(50), BIGINT 등

### ERD Cloud 사용할때 논리, 물리 필드명
- 논리 필드명
  - 데이터의 의미를 설명하기 위한 부가적인 정보
  - 실제 쿼리 포함 X
  - Key, Domain, Comment
- 물리 필드명
  - 데이터베이스에 실제로 저장되거나, 쿼리에 포함되어 처리되는 실제 값
  - Field, Type, NULL 유무, Default value

### Identifying Relationship
- 식별 관계
- ERD Cloud에서는 실선으로 표현
- 부모 테이블의 기본키를 자식 테이블에서도 기본키로 사용

### Non-Identifying Relationship
- 비식별 관계
- ERD Cloud에서는 점선으로 표현
- 부모 테이블의 기본키를 자식 테이블에서 외래키로 사용

ERD 작성할때 주의해야할 제약 조건
1. 기본키 선정
   - 고유값을 가짐 + NULL 값 허용하지 않음
2. 부모 테이블 & 자식 테이블 설정
   - 자식 테이블이 부모 테이블의 기본키를 가지고 있음 + 기본키로 사용 -> 실선
   - 자식 테이블이 부모 테이블의 기본키를 가지고 있음 + 기본키로 사용 X -> 점선
3. 테이블 간 중복된 컬럼이 있으면 안됨
   - 정규화 규칙에 따름
      1. 테이블 간 중복되는 컬럼이 있는지 확인
      2. 중복이 된다면 같은 컬럼인지 확인 후 자식 테이블 중복 컬럼 삭제
      3. 같은 컬럼이 아니라면 부모, 자식 테이블중 하나의 컬럼명 변경
      4. 바꾼 컬럼명이 용어로 등록되어 있지 않으면 등록
4. 명명 규칙
   - 테이블명은 복수형을 주로 사용
