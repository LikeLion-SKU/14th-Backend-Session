관계형 데이터베이스
-> 데이터를 행과 열로 구성하는 데이터베이스 유형

관계형 데이터베이스의 이점
직관적인 데이터 구조
데이터 무결설 보장(프라이머리, 포린 키로 데이터 관계 유지)
SQL 기반 데이터 조희
데이터 정규화 지원(데이터 중복을 줄이고 데이터 구조를 체계적으로 정리하는 설계 기법), 데이터 중복 감소 및 데이터 일관성 유지
ACID 트랜잭션 지원(원자성,일관성,격리성,지속성 보장)


연관 관계
-> 객체 지향과 관계형 데이터베이스의 관계 표현 방식

테이블 사이의 자연스러운 매핑이 필요하기 때문에 ORM 기술을 사용

연관 관계 정의 규칙

방향 (단반향, 양방향)

연관 관계 주인 (양방향 연관 관계에서 외래키를 관리하는 주체)

다중성

연관 관계 방향
관계형 데이터베이스
-> 외래키를 통해 양쪽 테이블 조인 가능
-> 방향 개념이 존재하지 않음

객체 지향 프로그래밍
참조 필드가 있는 객체만 접근 가능
단방향,양방향 연관 관계로 나뉨

단방향 연관 관계
한쪽 엔티티만 다른 엔티티를 참조하는 구조

양방향 연관 관계
양쪽 엔티티가 서로를 참조하는 구조

연관 관계의 주인

주인
외래키 등록 / 수정 / 삭제 가능
joinColumn 사용
외래키가 있는 테이블이 주인이 됨
1:N N:1 관계에서 N쪽이 외래키를 가짐

OneToMany를 왜 지양할까
불필요한 조회 가능성  N + 1 문제 발생 가능
객체 상태 관리 부담(양쪽 객체를 직접 맞춰줘야 함) -> 실수 시 데이터 불일치 발생
실제 연관관계 주인은 따로 존재 외래키 관리 = ManyToOne OneToMany는 mappedBy는 읽기전용

단방향 지향 : ManyToOne을 사용하고 레포지토리에서 쿼리 사용


FetchType : 연관된 엔티티 조회 전략
즉시 로딩 : 엔티티 조회 시 연관된 데이터까지 DB에서 함께 조회하는 방식
장점 : 데이터를 추가 조회 없이 바로 사용 가능
단점 : 조인 쿼리가 복잡해지고 성능 저하 발생 가능, 조회하지 않는 연관 데이터까지 DB에서 가져옴

지연 로딩 : 연관된 데이터를 실제로 사용하는 시점에 DB에서 조회
장점 : 필요 시점에만 조회 -> 불필요한 DB 조회 방지(처음에는 실제 데이터가 아닌 프록시 객체로 조회되고
해당 데이터에 접근하는 순간 DB 쿼리가 실행됨)

JPA에서는 성능 최적화를 위해 지연 로딩 사용을 권장함

여기서 성능 최적화는 데이터를 언제 얼마나 DB에서 가져오느냐

실무관계에선 LAZY를 사용하고 필요 시 FetchType

다중성
-> 엔티티 간 관계에서 한 객체가 다른 객체와 몇 개의 관계를 가질수 있는지를 의미

다대일(N:1)
@ManyToOne
Ex . 여러 게시글이 한 사용자를 참조

일대다(1:N)
@OneToMany
Ex. 한 사용자가 여러 게시글을 작성

일대일(1:1)
@OneToOne
Ex. 한 사용자가 하나의 프로필을 가짐

다대다(N:M)
@ManyToMany
게시글에는 여러 태그가 달릴 수 있고 하나의 태그는 여러 게시물을 적용

관계를 표현 가능하지만 실무에서는 조인을 사용하여 분리하여 사용함

왜 다대다를 그대로 쓰지않을까?
@ManyToMany는 관계 정보를 저장할 수 없기 때문

CasCade
-> 부모 엔티티의 영속성 작업을 연관된 자식 엔티티에 전파하는 기능
부모 엔티티가 변경될 때 자식 엔티티도 함께 처리됨
장점 : 개별적으로 관리할 필요 없음, 코드가 간졀해지고 유지보수가 쉬움

종류
ALL, PERSIST(부모 엔티티를 저장할 때 자식 엔티티도 함께 저장), REMOVE, MERGE, REFRESH, DETATCH

orphanRemoval 이란?
부모 엔티티와의 연관 관계가 끊어진 자식 엔티티를 DB에서 자동으로 삭제하는 옵션
@OneToMany에서 사용

orphanRemoval 해당 member 삭제
Cascade REMOVE member 전체 삭제

Cascade 주의사항
강하게 의존하는 관계에서 사용하는 것이 적절
ERD
-> 데이터베이스를 실제로 구현하기 전에 데이터 구조와 테이블 간 관계를 시작적으로 표현하는 설계 도구


Domain VS Type

Domain
데이터의 의미를 논리적 데이터 타입

Type
데이터의 의미를 물리적 데이터 타입

ERD 설계 필요성
데이터 중복을 줄이고 구조를 명확하게 설계할 수 있으며 개발자 간 협업에도 도움이 됨

체계적으로 설계 가능
관계 명확화
중복 최소화
협업 및 구조 이해 용이
설계 검증 가능

ERD 작성 시 유의사항 
개체 무결성 제약 조건 
    NULL 값을 가질 수 없으며(Not Null), 중복된 값을 가질 수 없습니다(Unique).

참조 무결성 제약 조건  
    참조하는 부모 테이블의 기본키에 존재하는 값만 입력할 수 있거나, NULL 값이어야 합니다.
 
도메인 무결성 제약 조건 
    Not Null: 해당 컬럼에 빈 값을 허용하지 않습니다. (예: 이름, 아이디)
    Unique: 중복된 값을 허용하지 않지만, NULL은 허용할 수 있습니다. (예: 이메일, 전화번호)
    Check: 특정 범위나 조건을 만족하는 값만 허용합니다.
